### AUTH-001 — Expired Codex sign-in needs an in-place recovery path

- **Status:** In progress
- **Problem:** When Codex access expires or its refresh token is revoked, the raw provider diagnostic is surfaced as a generic failed response and leaves a useless Retry action. The user needs a clear way to sign in again without losing the task they were doing.
- **Decision:** Classify expired or revoked Codex authentication separately from ordinary failures, keep that recovery state independent of the durable account boundary, and show an attached amber `Sign in required` recovery surface with an obvious `Sign In` action plus a restrained `Open Settings` fallback. While that card is attached, it owns the authentication state: suppress its failure-styled transcript duplicate without deleting provider history. Use plain language with no token jargon, suppress duplicate modal notices, and hide Retry while reauthentication is pending. Preserve the selected task, transcript, workspace, composer draft, and accepted follow-up queue. Clear recovery only after the login ceremony and an authoritative signed-in account refresh; a stale signed-in event alone is not enough. Keep pending approvals or input visible but non-authorizing until a fresh interaction is issued or confirmed. An authoritative signed-out notification or account replacement still closes the account boundary and clears account-owned state, and successful reauthentication must reconcile every attached window. A replacement account re-enters the normal connection/catalog bootstrap while keeping New Task selected, so its task list appears without implicitly opening a private transcript. Once the signed-out boundary is authoritative, late app-server stop/disconnect/runtime notices remain hidden behind the recovery surface. A `model/list` authentication failure is authoritative even when `account/read` returns a stale signed-in snapshot, so Onyx must not project a healthy session.
- **Acceptance:** An expired Codex request or notification produces one attached `Sign in required` card with human-readable detail and reachable `Sign In` and `Open Settings` actions. No raw token text, duplicate transcript failure, duplicate modal, or dead Retry control is shown. The task, transcript, workspace, and composer draft remain intact; Retry returns only after login plus authoritative signed-in refresh and selected-thread state is reconciled. Pending approval/input cannot be auto-authorized from stale state. Authoritative signed-out or account-replacement events invoke the destructive boundary rather than being mistaken for transient recovery, including in sibling windows.
- **Verification:** Runtime, projection, app-model, coordinator, writer, and presentation coverage now classifies raw request, notification, and stderr failures; both observed 401 `token_invalidated` diagnostics (analytics upload and model-catalog refresh) open recovery without exposing their JSON in a modal. Sessionless `account/read` recovery keeps the initialized transport alive for browser or device-code sign-in, then reconnects and reloads the catalog after successful authentication. App-model handling now also routes catalog refresh, selected-task reads, New Task and archived-list refreshes, earlier-history pagination, notification-triggered refreshes, reconnect resume, and uncertain-edit reconciliation through the same attached recovery surface instead of generic notices or a replacement error transcript. If access expires while opening another task, Onyx rolls back to the fully visible task instead of leaving a blank transcript under the clicked row. Authentication-classified connection failures no longer erase pending approval/input context or queued follow-ups, and stale request IDs stay quarantined. Login-start and login-completion paths also suppress raw credential diagnostics. Recovery retires an ephemeral side chat so late fork events cannot resurrect a hidden spinner or leak into the durable task. Late app-server stop/disconnect/runtime/recovery events after authoritative sign-out are suppressed, and model-catalog authentication failures are no longer swallowed when `account/read` is stale. A debug-only, credential-free preview fixture mounts the real shared-runtime/window composition with a task, transcript, workspace, draft, accepted follow-up, and pending approval, then emits expired-session recovery without touching real credentials; its host-level regression confirms that seeded state survives the shared coordinator. Replacement-account coverage confirms the old account is cleared, New Task stays selected, and the new account's catalog reloads. The complete local suite passes 1,056 tests with 17 intentional skips and zero failures when loopback listener access is available. The reported raw model-refresh modal was timestamped before the classifier and recovery path landed; public `v0.1.6` contains that classifier. On 2026-08-29, the canonical `Onyx Preview` fixture visibly showed one attached `Sign in required` card with `Open Settings` and `Sign In`, no raw JSON or modal, the original transcript and workspace, the preserved composer draft and queued follow-up, and a visible but disabled pending approval. A future natural expiration plus successful sign-in cycle remains pending, so this issue stays **In progress**.

- **Presentation race follow-up:** The workspace alert binding now fails closed while authentication recovery is active, so a stale SwiftUI transaction cannot leave raw JSON covering the `Sign In` and `Open Settings` actions. Focused presentation coverage protects this boundary.

### RELEASE-002 — Installing a release must replace stale local Onyx copies

- **Status:** In progress
- **Problem:** Downloading or opening a DMG does not replace an already-installed `/Applications/Onyx.app`. macOS can therefore reopen an older same-bundle copy, making a current dark release appear stale; an ad-hoc build can also stop at Gatekeeper before the user reaches the new app.
- **Decision:** Make the install handoff explicit: quit the running app, drag the DMG's `Onyx.app` to `Applications`, choose **Replace**, and document the one-time **System Settings → Privacy & Security → Open Anyway** or Control-click → **Open** path. Keep this separate from the future Developer ID/notarization gate.
- **Acceptance:** A user can identify the installed app as the downloaded release (version, source revision, and dark baseline), cannot accidentally relaunch the prior same-ID copy, and has a clear safe recovery path when Gatekeeper blocks the ad-hoc first launch.
- **Verification:** Public API and downloaded-artifact inspection prove `v0.1.6` is latest, checksum-valid, universal, and source-revisioned to `86d71d19a90e73574d698521b55685292fa5578d`; the same app code is running in the restrained near-black canonical preview. Local `/Applications/Onyx.app` was independently observed as stale `0.1.0` build `3` with the pre-dark marker. README and releasing docs explain replacement and Gatekeeper recovery. User-facing drag-to-Applications, choose-Replace, and launch verification remains pending, so this issue stays **In progress**.

### UI-003 — The latest message cannot be edited

- **Status:** In progress
- **Problem:** A user cannot correct and resubmit their most recent message as they can in Codex.
- **Decision:** Use the provider's exact history-revert operation for the latest completed, failed, or interrupted user turn. Codex uses its native server operation; OpenAI-compatible providers use an atomic operation over their Onyx-owned history. Show a recognizable inline `Edit` action on that message with a generous 32×32 pt target; selecting it turns the latest user bubble into an inline editor with Save/Cancel actions and does not open a confirmation modal or move the text into the bottom composer. A failed latest turn shows a recovery action attached to the failed response row (not as a detached floating control), which removes that turn and sends the original input exactly once. Before the first destructive edit or retry, explain that conversation history after that point is removed but workspace file changes are not reverted and may be repeated by Retry. A provider turn containing multiple user messages is not editable as one message because reverting it would remove all of them. While a revert is pending, keep typing responsive but block other writer operations; Edit merges later draft input, while Retry sends only the failed input and preserves later typing as the next draft. An ambiguous provider outcome must reload authoritative history before unlocking Send. If that reload fails or the user has navigated elsewhere, keep the original task locked until its successful reopen without blocking unrelated tasks. Older Codex binaries that reject native revert lose the capability for the runtime session.
- **Acceptance:** The latest user message has an easy-to-discover labeled Edit action; activating it turns that same message row into an inline editor with the original text and attachments, Save/Cancel controls, no modal, and no jump to the bottom composer; cancel is lossless; submitting the edit resumes from the corrected message without duplicating it. A failed latest response has a visible Retry action visually attached to the failure row; Retry removes the failed turn, submits the exact original input once, and retains any unrelated draft typed while it prepares. Older messages remain read-only for now.
- **Verification:** Automated coverage passes for the visible-at-rest 32×32 edit action, inline editor geometry and Save/Cancel behavior, failure-row Retry including narrow geometry and attachment, older-message read-only behavior, native and app-owned provider revert, stable/legacy provider turn identity, restored text and image attachment, corrected resubmission without duplication, exact failed-turn retry, pre-acceptance send failure cleanup of the exact optimistic user row while restoring its draft, draft typing during a suspended retry, steered-turn safety, stale callbacks, concurrent draft typing, concurrent history pagination, writer-operation gating, ambiguous-outcome reconciliation, retained lock after failed reconciliation or navigation away, unrelated-task Edit/Retry availability, runtime-replacement protection against erasing a newer durable turn, and runtime capability downgrade. Running-build verification of multiline inline editing, attachment preview, Retry placement, and unavailable state during active work is still pending, so this remains **In progress**.

### PERF-001 — Large tasks should appear tail-first

- **Status:** In progress
- **Problem:** Opening a large task feels slow because the user waits for the full transcript even though they usually need its most recent page.
- **Decision:** Render the newest page of a task first, keep scrolling/input responsive, and load older content incrementally above it. Codex reads metadata plus its 12 newest turns without acquiring writer ownership; reconnecting or sending resumes the task explicitly. An older Codex server that explicitly rejects the pagination method or parameters falls back to its full read/resume while Onyx still presents only the newest 120 items. Other provider or transport failures remain visible. Other providers present at most 120 already-read items initially. Every older reveal is also capped at 120 items, including an unusually large provider turn. A quiet “Load earlier messages” action fetches or reveals the next page. Prepending uses native row insertion and anchors the visible row rather than reloading the transcript or moving the reader.
- **Acceptance:** A large task shows its latest useful content immediately with an in-context loading indication for older history; the composer remains interactive; older pages load on demand or in idle time; prepending a page does not move the content currently under the reader’s eyes.
- **Verification:** Provider-tail, explicit-empty-page, suspended older-page, buffered-fallback, compatibility-fallback, constant-time planning, and hosted scroll-anchor regressions pass. Compatibility coverage exercises both JSON-RPC method-not-found and invalid-params, legacy resume before send, the 120-item bound, and refusal to fall back for unrelated failures. The hosted native view confirms valid prepends insert rows without a full reload and preserve the visible offset within 1 pt. A 20,000-row mixed conversation with grouped activity survives three older-page prepends plus 100 assistant/tool tail mutations without materializing history, rebuilding the full row index, or reloading the full projection. Additional hosted coverage verifies assistant-only history pages still shift all expected activity identities into the final rollup and that an appended plan remains the exact mounted row refreshed beyond the near-tail lookup budget. Running-preview measurement is intentionally still pending, so this issue remains **In progress**.

### PROVIDER-008 — Generic Responses requests must not inherit vLLM's tiny output default

- **Decision:** Keep the provider/model path generic. When app-server 0.149.0 reports the known `stream disconnected before completion: Incomplete response returned, reason: max_output_tokens` diagnostic, project it as a clear output-limit failure instead of a transport disconnect; unrelated disconnect errors remain unchanged.
- **Acceptance:** Any compatible model can complete reasoning/tool turns that exceed 2,048 output tokens without a false disconnect; explicit output budgets still pass through unchanged; models with smaller advertised limits are not overrun; malformed or oversized requests fail before credentialed forwarding; a truncated turn is never silently replayed; and a genuine output-limit failure is explained as such in both live and persisted history.
