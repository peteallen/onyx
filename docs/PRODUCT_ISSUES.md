### RELEASE-002 — Installing a release must replace stale local Onyx copies

- **Status:** In progress
- **Problem:** Downloading or opening a DMG does not replace an already-installed `/Applications/Onyx.app`. macOS can therefore reopen an older same-bundle copy, making a current dark release appear stale; an ad-hoc build can also stop at Gatekeeper before the user reaches the new app.
- **Decision:** Make the install handoff explicit: quit the running app, drag the DMG's `Onyx.app` to `Applications`, choose **Replace**, and document the one-time **System Settings → Privacy & Security → Open Anyway** or Control-click → **Open** path. Keep this separate from the future Developer ID/notarization gate.
- **Acceptance:** A user can identify the installed app as the downloaded release (version, source revision, and dark baseline), cannot accidentally relaunch the prior same-ID copy, and has a clear safe recovery path when Gatekeeper blocks the ad-hoc first launch.
- **Verification:** Public API and downloaded-artifact inspection prove `v0.1.3` is latest, checksum-valid, universal, source-revisioned, and contains the restrained near-black marker; local `/Applications/Onyx.app` was independently observed as stale `0.1.0` build `3` with the pre-dark marker. README and releasing docs explain replacement and Gatekeeper recovery. User-facing drag-to-Applications, choose-Replace, and launch verification remains pending, so this issue stays **In progress**.

### UI-003 — The latest message cannot be edited

- **Status:** In progress
- **Problem:** A user cannot correct and resubmit their most recent message as they can in Codex.
- **Decision:** Use the provider's exact history-revert operation for the latest completed, failed, or interrupted user turn. Codex uses its native server operation; OpenAI-compatible providers use an atomic operation over their Onyx-owned history. Show a recognizable inline `Edit` action on that message with a generous 32×32 pt target; selecting it turns the latest user bubble into an inline editor with Save/Cancel actions and does not open a confirmation modal or move the text into the bottom composer. A failed latest turn shows a recovery action attached to the failed response row (not as a detached floating control), which removes that turn and sends the original input exactly once. Before the first destructive edit or retry, explain that conversation history after that point is removed but workspace file changes are not reverted and may be repeated by Retry. A provider turn containing multiple user messages is not editable as one message because reverting it would remove all of them. While a revert is pending, keep typing responsive but block other writer operations; Edit merges later draft input, while Retry sends only the failed input and preserves later typing as the next draft. An ambiguous provider outcome must reload authoritative history before unlocking Send. If that reload fails or the user has navigated elsewhere, keep the original task locked until its successful reopen without blocking unrelated tasks. Older Codex binaries that reject native revert lose the capability for the runtime session.
- **Acceptance:** The latest user message has an easy-to-discover labeled Edit action; activating it turns that same message row into an inline editor with the original text and attachments, Save/Cancel controls, no modal, and no jump to the bottom composer; cancel is lossless; submitting the edit resumes from the corrected message without duplicating it. A failed latest response has a visible Retry action visually attached to the failure row; Retry removes the failed turn, submits the exact original input once, and retains any unrelated draft typed while it prepares. Older messages remain read-only for now.
- **Verification:** Automated coverage passes for the visible-at-rest 32×32 edit action, inline editor geometry and Save/Cancel behavior, failure-row Retry including narrow geometry and attachment, older-message read-only behavior, native and app-owned provider revert, stable/legacy provider turn identity, restored text and image attachment, corrected resubmission without duplication, exact failed-turn retry, pre-acceptance send failure cleanup of the exact optimistic user row while restoring its draft, draft typing during a suspended retry, steered-turn safety, stale callbacks, concurrent draft typing, concurrent history pagination, writer-operation gating, ambiguous-outcome reconciliation, retained lock after failed reconciliation or navigation away, unrelated-task Edit/Retry availability, runtime-replacement protection against erasing a newer durable turn, and runtime capability downgrade. Running-build verification of multiline inline editing, attachment preview, Retry placement, and unavailable state during active work is still pending, so this remains **In progress**.

### PERF-001 — Large tasks should appear tail-first

- **Status:** In progress
- **Problem:** Opening a large task feels slow because the user waits for the full transcript even though they usually need its most recent page.
- **Decision:** Render the newest page of a task first, keep scrolling/input responsive, and load older content incrementally above it. Codex reads metadata plus its 12 newest turns without acquiring writer ownership; reconnecting or sending resumes the task explicitly. An older Codex server that explicitly rejects the pagination method or parameters falls back to its full read/resume while Onyx still presents only the newest 120 items. Other provider or transport failures remain visible. Other providers present at most 120 already-read items initially. Every older reveal is also capped at 120 items, including an unusually large provider turn. A quiet “Load earlier messages” action fetches or reveals the next page. Prepending uses native row insertion and anchors the visible row rather than reloading the transcript or moving the reader.
- **Acceptance:** A large task shows its latest useful content immediately with an in-context loading indication for older history; the composer remains interactive; older pages load on demand or in idle time; prepending a page does not move the content currently under the reader’s eyes.
- **Verification:** Provider-tail, explicit-empty-page, suspended older-page, buffered-fallback, compatibility-fallback, constant-time planning, and hosted scroll-anchor regressions pass. Compatibility coverage exercises both JSON-RPC method-not-found and invalid-params, legacy resume before send, the 120-item bound, and refusal to fall back for unrelated failures. The hosted native view confirms valid prepends insert rows without a full reload and preserve the visible offset within 1 pt. A 20,000-row mixed conversation with grouped activity survives three older-page prepends plus 100 assistant/tool tail mutations without materializing history, rebuilding the full row index, or reloading the full projection. Additional hosted coverage verifies assistant-only history pages still shift all expected activity identities into the final rollup and that an appended plan remains the exact mounted row refreshed beyond the near-tail lookup budget. Running-preview measurement is intentionally still pending, so this issue remains **In progress**.

### D-020 — Provider credentials commit through versioned Keychain slots
